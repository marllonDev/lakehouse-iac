# lakehouse-iac

[![docs](https://img.shields.io/badge/docs-lineage%20graph-1a73e8)](https://marllondev.github.io/lakehouse-iac/)
[![ci](https://github.com/marllonDev/lakehouse-iac/actions/workflows/ci.yml/badge.svg)](https://github.com/marllonDev/lakehouse-iac/actions/workflows/ci.yml)

A small analytics platform on **Databricks Free Edition** where the platform
itself is code: **Terraform** provisions and governs the Unity Catalog objects
and the jobs, **dbt** owns every relation inside them, and the dbt builds run on
Databricks, not on a developer machine.

📖 [SPEC.md](SPEC.md) — what each tool owns and why · [USAGE.md](USAGE.md) — how
to run and change every folder · [ARCHITECTURE.md](ARCHITECTURE.md) — the system
map and the decisions behind it · [BENCHMARK.md](BENCHMARK.md) — dbt Core vs dbt v2 · [docs site](https://marllondev.github.io/lakehouse-iac/) — model lineage, generated by `dbt docs`

The point of the project is the seam between those two tools. Terraform and dbt
will happily both try to own a schema, and the result is drift and destroyed
tables. Here the line is drawn explicitly:

| Layer | Owner | What it manages |
|---|---|---|
| Catalog, schemas, grants, jobs | Terraform | The containers, who may read them, and what runs |
| Tables, views, tests | dbt | The relations inside those containers |

`generate_schema_name` is overridden so dbt writes into the exact schema names
Terraform created, instead of dbt's default `<target>_<custom>` mangling.

## What it builds

A 146-model dbt project over four read-only datasets that ship in every
Databricks workspace, sized so that the difference between dbt engines can be
measured:

| Dataset | What it is | Largest table |
|---|---|---|
| `samples.tpch` | Wholesale supplier | 30M order lines |
| `samples.tpcds_sf1` | Retail star schema, three sales channels | 11.7M inventory rows |
| `samples.wanderbricks` | Short-term rental marketplace, with real-data quirks | 500k page views |
| `samples.clickbench` | Web analytics events | 100M events |

```
samples.*  ──▶  staging (49 views)  ──▶  intermediate (25 views)  ──▶  marts (72 tables)
```

| | |
|---|---|
| Models | 146: 49 staging, 25 intermediate, 72 marts |
| Seeds, snapshots | 3 seeds, 2 snapshots |
| Tests | 398 data tests, 4 unit tests, 11 of the data tests written as singular SQL |
| Nodes per `dbt build` | 553 |

The staging, intermediate and mart models beyond the original TPC-H ones are
written as data in `scripts/generate/` and generated, so a model and its tests
sit side by side in one place. The generated SQL and YAML are committed.

`fct_orders`, `fct_wb_bookings` and `fct_wb_payments` are incremental merges.
`fct_orders` reprocesses a three-day trailing window on `order_key`, so
late-arriving order lines are picked up without rebuilding 7.5M rows.

## dbt Core and dbt v2, on Databricks

Two jobs run the same project, one engine each, through the same Python runner
([`jobs/run_dbt.py`](jobs/run_dbt.py)). The native `dbt_task` supports only dbt
Core, so a shared runner is what makes the comparison fair. It authenticates with
the job's own identity: no personal access token, no secret in any file.

| Job | Engine |
|---|---|
| `dbt-core` | dbt Core 1.12 + `dbt-databricks` 1.12.4 |
| `dbt-v2` | dbt v2, `dbt==2.0.6` |

Same commit, same serverless environment version 6, same warehouse, same
threads, one job at a time. Six alternating runs after a discarded warm-up, of
the same 553-node build:

| Step | dbt Core | dbt v2 |
|---|---:|---:|
| `parse` | 10.9 s | 1.0 s |
| `compile` | 16.1 s | 2.5 s |
| `build` | 232 s | 214 s |

dbt v2 parses and compiles 6 to 11 times faster. The build is bound by the
warehouse, which is busy about 215 seconds under either engine, so v2 saves the
dbt-side overhead only: about 8% of the build. Both engines touched the same 553
nodes with the same results, and 147 of 151 relations have identical checksums;
the other four are non-deterministic under either engine. Method, caveats and
what was not measured are in [BENCHMARK.md](BENCHMARK.md).

The original `tpch-batch` job, dbt Core through the native `dbt_task`, is still
there as the reference implementation.

## Running it

Everything the local machine needs is installed inside the repository. The only
prerequisite is [uv](https://docs.astral.sh/uv/).

```bash
bash scripts/install-tools.sh      # terraform + databricks CLI into .bin, dbt into .venv
source scripts/env.sh              # put them on PATH, set connection env vars
databricks auth login --host https://<your-workspace>.cloud.databricks.com --profile FREE

terraform -chdir=infra init
terraform -chdir=infra apply -var environment=dev

databricks jobs run-now "$(terraform -chdir=infra output -raw tpch_batch_job_id)"
```

Every job clones this repository over `git_source`, so Databricks needs a Git
credential linked the first time — see [USAGE.md](USAGE.md#the-job-and-why-it-needs-github).

Working on this repo with an AI assistant is optional and not part of the
pipeline. Databricks agent skills are installed once per machine, not per
repository: `databricks aitools install --agents claude-code --scope global`.

## Free Edition constraints, and what they forced

Free Edition is not a cut-down API — it is a real workspace with no cloud
account attached, and that changes what infrastructure code can do. Measured
against the live workspace:

| Operation | REST API (what Terraform uses) | SQL |
|---|---|---|
| Create catalog | ✗ rejected — Default Storage | ✓ |
| Create schema | ✓ | ✓ |
| Grants | ✓ | ✓ |
| Create SQL warehouse | ✗ — only the bundled Starter | — |
| Create job | ✓ | ✓ |

Two consequences are visible in the Terraform code:

1. **The catalog is created over SQL.** `databricks_catalog` calls a Unity
   Catalog endpoint that refuses to run without a storage root, and Free Edition
   has no storage location to give it. The equivalent `CREATE CATALOG` statement
   resolves Default Storage on its own, so `terraform_data.catalog` shells out to
   `scripts/uc-catalog.sh`. Its destroy provisioner drops the catalog, so
   `terraform destroy` still leaves nothing behind.
2. **The SQL warehouse is a data source, not a resource.** Free Edition ships one
   warehouse and will not create another, so Terraform looks it up by name and
   feeds its HTTP path to dbt through an output.

Both are deliberate: the code stays honest about the boundary rather than
pretending an unavailable API works.

## Layout

```
infra/          Terraform: catalog, schemas, grants, warehouse lookup, the jobs
transform/      dbt project: sources, staging, intermediate, marts, seeds, snapshots, tests
jobs/           Python entry point that runs dbt, either engine, inside a Databricks job
benchmarks/     Raw numbers of the engine comparison
scripts/        tool installation, environment, catalog bootstrap, model generators, docs publish
.github/        CI: format, validate, dbt parse
```

See [USAGE.md](USAGE.md) for what every file in each folder does, and
[ARCHITECTURE.md](ARCHITECTURE.md) for the system diagrams and the decisions —
including the ones that turned out wrong on the first try — behind how it fits
together.
